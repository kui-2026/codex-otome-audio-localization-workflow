# Codex乙抓汉化工作流

**Codex-assisted Japanese Otome Audio Localization Workflow**

这是一个以 OpenAI Codex 作为主要执行助手的日语女性向音声（乙抓）本地化工作流与工程模板。

项目记录了从合法取得的原始音声和日文台本出发，使用 Codex 协助完成文件整理、文本编码修复、台本翻译、语音识别辅助、台本与音频时间轴匹配、简体中文字幕生成、无损 FLAC 转换、封面及元数据写入、同步歌词内嵌和质量验证的完整流程。

本仓库只提供通用脚本、配置模板、提示词模板和操作说明，不包含或分发任何受版权保护的原始音声、台本、商品图片、翻译成品或字幕文件。使用者必须自行合法取得素材，并遵守作品的使用条款。

## 项目简介

本项目的中文定位是：**Codex 辅助乙抓汉化工作流与本地工程模板**。

它把一次音声本地化任务拆成可检查、可复用、可回退的步骤，并强调原始素材只读保存、过程文件与最终成果分层管理、自动检查与人工抽查并行。仓库中的命令和示例只使用虚构的作品名、角色名与文本。

## 这是什么

- **这是一个工作流**：规定每一步应该如何处理、检查和交付。
- **这是一个工程模板**：可以为每一部新作品创建统一的 `source`、`work`、`final` 和 `archive` 目录。
- **这是一个环境配置指南**：说明如何安装 FFmpeg、Python、faster-whisper 等依赖。
- **它不是打包好的完整运行环境**。
- GitHub 仓库不附带 FFmpeg 二进制文件、Python 虚拟环境或 Whisper 模型。
- 用户需要按照安装说明在本机配置环境。
- Codex 负责根据提示词调用本地工具、组织文件、生成脚本并完成验证。

## 主要功能

- 日文台本编码检测及 UTF-8 修复
- 原始文件只读归档
- Codex 辅助日译中
- faster-whisper 日语 ASR 辅助
- 台本行与音频时间轴匹配
- LRC、SRT 和 VTT 字幕生成
- HTML 本地试听与字幕抽查
- WAV 无损转换为 FLAC
- 商品封面及音频元数据嵌入
- 带时间戳的 `LYRICS` 标签内嵌
- iPlayer 滚动中文字幕支持
- PCM 级无损一致性验证
- 可复用的新作品工程模板
- 原始文件、过程文件和最终成果分层管理

## 为什么使用 Codex

Codex 在这个工作流中用于：

- 识别和整理项目文件
- 编写及维护处理脚本
- 调用 `ffmpeg`、`ffprobe`、`metaflac` 和 Python 工具
- 翻译及校对日文台本
- 辅助匹配台本与语音时间轴
- 生成播放器兼容字幕
- 执行批量质量检查
- 生成制作报告

Codex 输出仍然需要人工抽查，尤其是翻译语气、角色关系、专有名词、ASR 识别结果及字幕同步。

## 工作流程

1. 合法取得素材，并把未经修改的副本放入 `source/`。
2. 生成文件清单、校验和与媒体探测报告。
3. 检测台本编码并统一生成 UTF-8 工作副本。
4. 建立术语表、角色表和翻译约定，完成初译与校对。
5. 使用 faster-whisper 生成日语 ASR 参考时间轴。
6. 将台本行与 ASR 片段匹配，人工处理低置信度和错位区间。
7. 生成简体中文 LRC、SRT、VTT，并通过本地试听页抽查。
8. 将 WAV 无损转换为 FLAC，写入经过授权使用的封面与元数据。
9. 将同步歌词写入 FLAC 标签，制作播放器导入目录。
10. 执行字幕、标签、时长、声道、采样率和 PCM 一致性验证。
11. 把交付文件放入 `final/`，把日志和中间版本放入 `archive/`。

## 台本编码修复

先检测编码，再生成新的 UTF-8 文件；永远不要直接覆盖原台本。常见日文文本可能使用 CP932、Shift_JIS 或 UTF-8。编码修复应同时记录：

- 原文件 SHA-256
- 检测到的编码及置信度
- 解码错误和替换字符数量
- UTF-8 输出文件 SHA-256
- 人工抽查的日文标点、波浪线、特殊符号和角色名

若检测结果不确定，应分别尝试候选编码并人工比对，不应仅凭自动检测结果批量覆盖。

## ASR 与台本对轴

ASR 只用于提供时间线索，不替代正式台本。建议先按静音或章节切分音频，再用日语模型生成带词级或片段级时间戳的参考结果。匹配时综合使用：

- 台本文字与 ASR 文本的相似度
- 片段时长与语速
- 停顿、章节和音效边界
- 上下文连续性
- 人工确认的锚点

对低置信度片段、多人重叠、耳语、环境音和 ASR 漏字建立单独的复核清单。

## 简体中文字幕生成

从同一份已确认的对轴数据生成不同格式，避免分别编辑造成版本漂移：

- LRC：适合逐行滚动歌词。
- SRT：适合常见视频和音频播放器。
- VTT：适合浏览器、本地 HTML 试听页和 Web 播放器。

字幕应检查时间戳递增、无负时长、无意外重叠、字符编码为 UTF-8，并控制单行长度和显示时间。翻译文本不得直接从未经人工确认的 ASR 结果生成最终版。

## WAV 无损转换为 FLAC

示例命令：

```powershell
ffmpeg -i "source.wav" -map_metadata 0 -c:a flac -compression_level 8 "output.flac"
```

FLAC 是无损压缩，但“无损”仍需验证。转换前后分别解码到规范化 PCM，并计算 SHA-256；只有 PCM 参数和哈希一致时，才能确认音频样本未改变。不要只比较 WAV 与 FLAC 文件本身的哈希。

## 同步歌词内嵌

先保留独立的 UTF-8 LRC 作为可审查源文件，再将其写入 FLAC 的 `LYRICS` 标签。写入后使用 `metaflac --list` 或等效工具读取标签，确认：

- 标签存在且只有预期版本
- 时间戳格式正确并单调递增
- 中文字符没有乱码
- 音频流参数和 PCM 内容未改变

不同播放器对同步歌词标签的支持并不完全一致，因此独立 LRC 文件应作为兼容性后备。

## iPlayer 导入方法

1. 准备已验证的 FLAC 文件，并确保文件名和轨道号排序一致。
2. 按播放器支持方式，将同步歌词写入 `LYRICS` 标签或把同名 `.lrc` 放在音频旁。
3. 通过 iPlayer 的本地文件、文件共享或其当前版本提供的导入入口传入文件。
4. 在播放器中检查中文编码、滚动位置、封面、专辑名、艺术家、轨道号和章节顺序。
5. 若播放器未读取内嵌歌词，保留 FLAC 不变，改用同名 LRC 兼容方案。

iPlayer 的具体导入界面和标签兼容性可能随版本变化，应以用户当前安装版本为准。

## 质量验证

发布本地成果前至少检查：

- 原始文件未被修改，SHA-256 记录完整
- 所有文本均为预期的 UTF-8 编码
- 字幕时间戳合法、递增、无越界
- ASR 低置信度段落已人工复核
- 翻译语气、角色关系和专有名词已抽查
- FLAC 时长、采样率、位深、声道与源文件一致
- WAV 与 FLAC 的规范化 PCM 哈希一致
- 封面和元数据可被目标播放器读取
- 内嵌歌词可回读，中文没有乱码
- `source/`、`work/`、`final/`、`archive/` 分层正确
- 制作报告列出工具版本、命令、异常和人工决定

## 已知限制

- ASR 对耳语、气声、背景音乐、多人重叠和拟声词的识别可能不稳定。
- 自动对轴不能取代逐段试听，长音频通常需要人工锚点。
- 机器辅助翻译可能误判语气、亲疏关系、敬语和角色设定。
- LRC、FLAC 标签与封面在不同播放器上的兼容性存在差异。
- PCM 校验能确认音频样本一致，但不能证明元数据、章节或播放体验正确。
- 工具参数和安装方式可能随版本或操作系统变化。
